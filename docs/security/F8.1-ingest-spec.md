## 0. Contexto y superficie

Hay una rutina cloud de Claude Code que se ejecuta lunes y jueves. Lee webs no fiables con WebSearch y WebFetch. Después llama por HTTPS (PostgREST) a cuatro tipos de RPC con la publishable key (rol `anon`) y un `INGEST_TOKEN`:

- `guide.ingest_start_run(p_token, p_kind, p_dry_run)`
- `guide.ingest_context(p_token)`
- `guide.ingest_submit_event(p_token, p_run_id, p_payload)` y `guide.ingest_submit_news(p_token, p_run_id, p_payload)`
- `guide.ingest_finish_run(p_token, p_run_id, p_stats, p_errors)`

Son SECURITY DEFINER, propiedad de `postgres` y con `search_path = ''`.

Supuestos:
- La publishable key es pública.
- **El modelo que tiene el token procesa contenido hostil.** Hay que asumir que el token puede filtrarse.
- Por eso el diseño no intenta que el token sea imposible de robar. Busca que **robarlo valga poco**: solo crea borradores con topes, es revocable y caduca pronto, y cada fila pasa por revisión humana (regla 6).

Estado actual comprobado (2026-11-13):
- `anon` no tiene grants de tabla sobre `guide.events` ni policy de escritura.
- La guarda `events_before_write` no depende del rol. Cualquier sesión sin `is_admin()`, y sin la GUC `guide.draft_op='maintenance'` con rol bypassrls, solo puede hacer INSERT con `status='draft'`, `source='agent'`, `approved_at` y `reject_reason` nulos. El servidor fija `id`, `created_at` y `updated_at`. Por tanto, una función DEFINER que inserta en `events` sigue validada. No es el caso O6 de `content_drafts`.
- En `guide` no hay default ACL. Las funciones nuevas nacen con EXECUTE para PUBLIC.
- pgcrypto está en el schema `extensions`.

## 2. Requisitos obligatorios para jabali-javi (8.5)

Cada punto se verifica en 8.6 con un test en `supabase/tests/guide_rls_leaks.sql`, siempre dentro de una transacción con ROLLBACK.

### Token

- **J1 Formato y entropía.** El token es `cgi_` seguido de 64 caracteres hex en minúsculas, generados con `extensions.gen_random_bytes(32)` (256 bits). Lo genera **solo el servidor**, con la RPC de admin `guide.admin_create_ingest_token(p_label text, p_expires_days int)` (`assert_admin` primero, `p_expires_days` entre 1 y 30). Devuelve el texto plano **una sola vez** y no queda guardado en ninguna parte.
- **J2 Almacenamiento y comparación.**
  - `ingest_tokens.token_hash bytea not null unique`, con `octet_length = 32`.
  - El hash se calcula con `extensions.digest(convert_to(p_token,'UTF8'),'sha256')`.
  - La búsqueda es por igualdad sobre el índice único, nunca con comparación de texto en claro.
  - La tabla guarda además: `hint` (últimos 4 caracteres, para el panel), `label`, `created_at`, `created_by`, `expires_at`, `revoked_at`, `last_used_at`.
- **J3 Rechazo barato.** Primero se comprueba `p_token ~ '^cgi_[0-9a-f]{64}$'` (que además acota la longitud). Si no cumple, se responde el error uniforme sin calcular el hash ni leer tablas.
- **J4 Validez.** Un token vale solo si `revoked_at is null and expires_at > now()`. La caducidad máxima es de 30 días. Como mucho hay **2 tokens vigentes** a la vez, para permitir el solape durante la rotación. Crear un tercero da error.
- **J5 Revocación.** `guide.admin_revoke_ingest_token(p_id)` hace efecto inmediato y además cierra como `revoked` los runs abiertos de ese token. Es idempotente.
- **J6 Error uniforme.** Formato malo, token inexistente, revocado o caducado dan siempre `raise exception 'ingest_unauthorized' using errcode = '42501'`, sin `detail` ni `hint`. Ningún mensaje de error de las RPC concatena parámetros de entrada.
- **J7 Intentos fallidos.** No se inserta una fila por intento. Si se quiere métrica, se usa una sola fila por hora en `guide.job_health` o en una tabla equivalente, con UPSERT de contador y sin la IP ni el token.

### Exposición de las RPC

- **J8** Las cuatro `ingest_*` son **VOLATILE**, también `ingest_context`, que actualiza `last_used_at`. Así PostgREST no las ejecuta por GET con el token en la query string.
- **J9 Permisos.** Para cada firma exacta: `revoke all on function ... from public, anon, authenticated, service_role;` y después `grant execute ... to anon;`. Las RPC de admin de tokens y runs reciben grant solo a `authenticated` y llevan `assert_admin()`. Las funciones internas (cálculo de la `dedupe_key`, limpieza de URL, validadores) no tienen EXECUTE para ningún rol de la API.
- **J10 Defensa en profundidad.** La primera comprobación de cada `ingest_*`, tras J3, es `if (select auth.uid()) is not null then 42501`. Una sesión con usuario, sea admin o no, nunca entra por esta vía. Así la rama de admin de los triggers, que forzaría `source='manual'`, nunca se activa.

### Validación del payload

- **J11 Lista blanca de claves.** Si el payload trae una clave no listada, se rechaza la fila.
  - **Evento:** `title_es`, `title_en`, `description_es`, `description_en`, `event_type`, `starts_at`, `ends_at`, `all_day`, `location_text`, `item_id`, `url`, `price_text`, `source_url`, `confidence`, `note`, `excerpt`, `inferred`.
  - **Noticia** (se cierra con 8.5 y data-model): `title_es`, `title_en`, `summary_es`, `summary_en`, `category`, `published_on_source` (fecha), `source_url`, `source_name`, `confidence`, `note`, `excerpt`.
  - **Prohibidas siempre**, aunque el cliente las mande: `id`, `status`, `source`, `dedupe_key`, `agent_meta` (lo construye el servidor), `duplicate_of`, `approved_at`, `approved_by`, `published_at`, `reject_reason`, `created_at`, `updated_at`, `run_id`, `has_en`, `slug`, `image`/`media_id`, `author_note` (la «Nota de Xavi»), `noindex`.
- **J12 Tamaño.** `octet_length(p_payload::text) <= 16384`, `jsonb_typeof = 'object'` y profundidad 1 salvo `inferred` (array de strings). Cada valor tiene el tipo JSON esperado: no se aceptan números en texto ni objetos anidados.
- **J13 Longitudes.**
  - **Eventos:** las de los CHECK actuales (títulos ≤ 200, descripciones ≤ 2000, `location_text` ≤ 200, `price_text` ≤ 120, `url` ≤ 500, `source_url` ≤ 1000).
  - **Noticias:** títulos 1–200, resúmenes 1–1200, `source_name` ≤ 120, `source_url` ≤ 1000, `note` ≤ 500, `excerpt` ≤ 1000. Para la ingesta, el `excerpt` de eventos baja a ≤ 1000: es evidencia, no contenido.
  - Todo se aplica con `btrim` y vacío pasa a null.
  - En `guide.news` todo esto va como CHECK puro, no solo en la RPC.
- **J14 Caracteres.** Se rechazan:
  - controles `[[:cntrl:]]` en títulos y campos de una línea; en textos largos, los controles salvo `\n`;
  - bidi `U+202A–U+202E` y `U+2066–U+2069`;
  - zero-width `U+200B–U+200D`, `U+FEFF`;
  - `U+0000`.

  Normalización Unicode NFC si está disponible (`normalize(x, NFC)`).
- **J15 Fechas y enums.**
  - `starts_at` y `ends_at` deben ser ISO 8601 **con zona** y se convierten a `timestamptz` dentro de un `begin ... exception` que cuenta la fila como `invalid`.
  - Eventos: `starts_at` debe ser futuro (`not guide.event_is_past(...)`) y ≤ `now() + 18 months` (D71: confirmados y futuros); además, los CHECK existentes.
  - Noticias: `published_on_source` entre `now() - 30 days` y `now() + 1 day`.
  - `event_type` debe estar en la lista del CHECK y `category` en `news_categories` activas.
  - `confidence` debe ser un número entre 0 y 1.
  - `item_id`, si viene, debe ser un `gym` **publicado** de la lista de `ingest_context`; si no, la fila es inválida.
- **J16 Datos personales.** Se rechaza la fila si algún campo de texto (incluidos `note` y `excerpt`) contiene un email (`[^\s@]+@[^\s@]+\.[a-z]{2,}`) o un teléfono (secuencia de ≥ 9 dígitos con separadores opcionales). Se cuenta como `invalid:pii` en las stats.
- **J17 Eco del token.** Si `position(p_token in p_payload::text) > 0`, o si el payload contiene `sb_secret_`, `sb_publishable_` o `eyJ` seguido de un JWT, se rechaza la fila. Lo mismo se aplica a `p_stats` y `p_errors` en `finish_run`.

### Dedupe

- **J18 Clave calculada por el servidor.** La fórmula es:
  `dedupe_key = 'v1:' || encode(digest(lower(host(source_url)) || '|' || <fecha Madrid de starts_at o de published_on_source> || '|' || <título normalizado: unaccent, minúsculas, solo [a-z0-9] y espacios colapsados>, 'sha256'), 'hex')`.
  El cliente no la envía. Para noticias, la clave se calcula también por `source_url` canónica (después de J23), y la noticia es duplicada si coincide cualquiera de las dos.
- **J18b Liberar la clave.** RPC de admin `guide.admin_release_event_dedupe(p_id)`: solo para `status='rejected'` con `reject_reason='wrong_data'`. Cambia la clave por `'released:'||id`, así que la `dedupe_key` sigue siendo no nula y única. Pasa por la GUC atada a la fila (`release_dedupe:<id>`, comprobada contra `old.id`), nunca por un valor genérico. Es la única excepción a `event_provenance_immutable`. Si no se quiere ahora, queda como R2, pero entonces T11 queda como riesgo aceptado.
- **J19 Respuesta de duplicado.** Es `{"result":"duplicate"}` sin más información. Internamente, `ingest_runs.stats` cuenta `duplicate_rejected` aparte, para que Xavi lo vea.

### Escritura

- **J20 Solo borradores.** Las RPC insertan con `status='draft'`, `source='agent'`, `approved_at null` y `reject_reason null`, y nunca hacen UPDATE ni DELETE en `events` ni en `news`. Los modos son `INSERT … ON CONFLICT (dedupe_key) DO NOTHING` o comprobación previa en la misma transacción.
- **J21 Guarda de noticias.** Se crea `guide.news_before_write`, equivalente a `events_before_write`. Para no-admin solo permite INSERT con `status='draft'`, `source='agent'`, `published_at`, `approved_*` y `author_note` nulos, y el servidor fija `id`, `created_at` y `updated_at`. Para el admin, la procedencia (`source`, `source_url` del agente, `dedupe_key`, `agent_meta`, `run_id`) es inmutable. La transición a `published` solo la hace el admin. La guarda no depende del rol, para que siga validando aunque llame una DEFINER.
- **J22** Ninguna `ingest_*` toca la GUC `guide.draft_op`, en ninguna parte del código.
- **J23 URLs.**
  - **Formato:** `url`, `source_url` y cualquier URL de noticia empiezan por `https://` (para la ingesta, también `events.source_url`, aunque su CHECK admita `http`). Host con al menos un punto y TLD alfabético. Sin `@` antes del host, sin puerto, sin IP literal v4/v6, sin `localhost` ni `.local`/`.internal`. Si el host es punycode `xn--`, se acepta pero se marca en `agent_meta.note`, para que el panel lo destaque.
  - **Limpieza:** el servidor quita los parámetros `utm_*`, `fbclid`, `gclid`, `dclid`, `msclkid`, `mc_cid`, `mc_eid`, `_hsenc`, `_hsmi`, `igshid`, `ref`, `ref_src`, y también el fragmento.
  - **Acortadores:** si el host está en la lista (`bit.ly`, `t.co`, `tinyurl.com`, `goo.gl`, `ow.ly`, `buff.ly`, `lnkd.in`), la fila se rechaza.
- **J24 Allowlist de noticias.** `host(source_url)` de una noticia debe coincidir con un dominio de `guide.news_sources` activo o ser subdominio suyo. Si no, la fila es `invalid:source`. Las fuentes las da de alta solo el admin. En eventos no hay allowlist, pero si el host no está en `news_sources` se anota `agent_meta.note = 'fuente no listada'` para el panel.
- **J25** Ni `pg_net`, ni `http`, ni descarga de URLs en las RPC, triggers o cron de la ingesta. Sin campo de imagen en la ingesta.

### Lecturas

- **J26 `ingest_context` devuelve solo:**
  - límites del run (topes y filas restantes);
  - `news_sources` activas (`name`, `domain`, `kind`, `region`);
  - `news_categories` activas (`key`, `label_es`);
  - `event_type` permitidos;
  - gyms publicados (`id`, `name`, `slug`, ciudad);
  - opcionalmente, eventos `approved` futuros (`title_es`, `starts_at`, `location_text`), que ya son públicos.

  No devuelve nunca: borradores, rechazados, `dedupe_key`, `agent_meta`, `source_url` de eventos (columna no pública), suscriptores, opiniones, admins, `activity_log`, `ingest_runs` de otros tokens ni datos de `public`. La salida debe ser ≤ 64 KB.
- **J27 Lo que ve anon de `news`.**
  - Policy `news_select` para `anon` y `authenticated`: `using (status = 'published' or (select guide.is_admin()))`.
  - Grants por columna, sin `select` de tabla: `id`, `slug`, títulos, resúmenes, `category`, `source_name`, `source_url` (pública por D73: se cita la fuente), `published_at`, `author_note_es`/`_en`, `noindex`, `has_en`, `updated_at`.
  - **Fuera** del grant: `dedupe_key`, `agent_meta`, `run_id`, `source`, `reject_reason`, `approved_by`, `created_at` si no hace falta, y cualquier `excerpt`.
  - Sin policies de INSERT, UPDATE ni DELETE para `anon`. Para `authenticated`, solo con `is_admin()`.
- **J27b** Al aprobar, publicar o descartar, `agent_meta` se reduce a `{confidence}` o se pone a null (O5/D33-3). Si los CHECK `events_agent_meta_only_agent` lo impiden, se reduce a `{"confidence":x}`. Lo mismo al caducar.

### Runs y logs

- **J28 Contenido de `ingest_runs`.**
  - Columnas: `id`, `token_id` (FK, nunca el hash), `kind`, `dry_run`, `status` (`open`/`ok`/`error`/`abandoned`/`revoked`), `started_at`, `finished_at`, `calls`, `inserted`, `duplicates`, `duplicate_rejected`, `invalid` (por motivo), `stats jsonb` ≤ 4 KB con claves en lista blanca y valores numéricos, `errors` en texto plano ≤ 4 KB y sin controles (J14, J17).
  - Sin token, hash, IP, cabeceras ni payloads completos.
  - RLS activada; SELECT solo para admin; ninguna escritura desde la API salvo por las RPC.
  - `ingest_tokens` con RLS, SELECT de admin solo por RPC o por grant de columnas **sin** `token_hash`.
- **J29 Validación del run.** `submit` y `finish` exigen que el run exista, que `token_id` sea el del token presentado, que `status='open'`, que `started_at > now() - 2h` y que el `kind` coincida (`events`, `news` o `both`).

### Topes

- **J30 Concurrencia.** Las comprobaciones de topes se hacen bajo `pg_advisory_xact_lock(hashtext('guide.ingest'))`, para evitar carreras. El índice único parcial `on ingest_runs ((true)) where status = 'open'` garantiza 1 run abierto en total, no por token.
- **J31 Runs.**
  - Máximo 3 runs con `started_at > now() - 24h`, contando todos los estados y también los `dry_run`.
  - Antes de abrir, se cierran como `abandoned` los runs abiertos con más de 2 h, lo que evita que un run colgado bloquee la rutina.
  - El cron de salud también los cierra.
- **J32 Filas.** Por run, máximo 40 insertadas y 80 llamadas a `submit` (las inválidas también cuentan). Se aplica con un `update ingest_runs set calls = calls + 1 ... where id = ... and calls < 80 returning`.
- **J33 Tope global.** Si hay más de 150 borradores del agente pendientes (events + news, no caducados), `start_run` responde `queue_full`. Así, aunque roben el token, la cola no crece sin fin.
- **J34 `dry_run`** (D76). Valida todo y aplica los topes, pero no inserta: responde `would_insert` o `duplicate`. Cuenta para los 3 runs/24 h.

### Cron de salud

- **J35 Job `guide-ingest-health`** con pg_cron, siguiendo el patrón de `20261112225821`: SQL puro, función INVOKER sin EXECUTE para ningún rol de la API, sin `pg_net`.
  - Escribe en `guide.job_health` la fila `ingest` con el último run `ok` y no `dry_run`.
  - El panel avisa si no hay run OK en 4 días, si hay un run `abandoned` o `error`, si hay `duplicate_rejected` > 0, si un token caduca en ≤ 5 días o si hay runs fuera de la ventana lun/jue (R1).
  - El mismo job cierra los runs abiertos de más de 2 h.

### Registro y comprobaciones finales

- **J36** `events_log_activity` y el log de `news`: `by = 'agent'` cuando `not is_admin()` y `new.source = 'agent'`. Hoy, con anon, saldría `by = 'system'`. Nunca se registra `agent_meta`, `dedupe_key`, el token ni su hash. Los triggers de log sobre `ingest_tokens`, si existen, excluyen `token_hash`.
- **J37** Todos los CHECK nuevos son expresiones puras (`.ai/security-rls.md`).
- **J38 Tests de fuga en `guide_rls_leaks.sql`:**
  - anon sin token → 42501;
  - token con formato inválido, revocado o caducado → el mismo 42501;
  - payload con `status`, `approved_at`, `published_at`, `dedupe_key` o `id` → fila rechazada;
  - URL `javascript:`, `http:`, `user@host` o IP → rechazada;

## 4. Requisitos para osset-op (8.7)

## 6. Veredicto previo

**Opción A (RPC + token) ACEPTABLE, con condiciones. No se pide la Edge Function (B).**

Por qué A:
1. **B no elimina el riesgo principal.** La rutina seguiría teniendo un secreto visible para el modelo (T1, T2). El secreto cambia de sitio, pero no deja de estar expuesto.
2. **B empeora el radio de daño.** La Edge Function necesitaría la `service_role` o un rol con permisos de escritura. Un fallo en su validación en TypeScript expondría escrituras amplias. Con A, el código privilegiado son 4 funciones con `search_path=''`. Además, las guardas `events_before_write` y `news_before_write`, que no dependen del rol, y los CHECK puros validan **también** lo que esas funciones hagan mal.
3. **A deja más superficie auditable y menos piezas** (sin deploy ni secretos de función). La fuerza bruta es inviable (256 bits) y el error es uniforme.
4. El coste de A es aceptable y conocido: avisos esperados del linter por DEFINER ejecutable por anon, y que PostgREST no limita por IP (T4, sin escrituras por fallo).

**Condiciones:** J1–J40 y F1–F3 son obligatorios. En 8.6 se verifica cada uno con tests en transacción con ROLLBACK. Si falta alguno, hay **VETO** de 8.5. O1–O8 se verifican en 8.7.
